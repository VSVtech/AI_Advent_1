# День 26 — локальная LLM

Проверка 6 октября 2026. Модель `qwen2.5:7b` (Q4_K_M, около 4,7 ГБ) в уже установленной Ollama. Приложение и Ollama работают на одном компьютере. Облачные API, RAG и MemoryCurator не используются.

## Воспроизведение

1. Запустить Ollama: `pnpm rag:ollama`.
2. При отсутствии модели: `ollama pull qwen2.5:7b` при запущенной Ollama. Это скачивание модели; последующая генерация локальная.
3. Запустить приложение: `pnpm dev`.
4. Открыть `/local-chat` через пункт «Локальная LLM» в боковом меню.
5. Запустить `pnpm local:check` для трёх независимых запросов. Результат сохраняется в `.local-data/day26/check.json`. Другой адрес/модель: `pnpm local:check http://localhost:3000/api/local-chat qwen2.5:1.5b`.

Прямой HTTP-запрос к Ollama:

```bash
curl http://127.0.0.1:11434/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5:7b","messages":[{"role":"user","content":"Сколько будет 17 + 25?"}],"stream":false}'
```

Страница использует серверный `/api/local-chat`: GET возвращает установленные локальные модели с возможностью генерации; POST передаёт историю в Ollama `/api/chat` и отдаёт поток ответа. Эмбеддинговые и облачные модели исключены, переадресации не выполняются. Адрес сервера берётся из `LOCAL_OLLAMA_URL`, затем `RAG_OLLAMA_URL`, иначе `http://127.0.0.1:11434`; разрешён только HTTP loopback.

[Документация Ollama Chat API](https://docs.ollama.com/api/chat), [список моделей](https://docs.ollama.com/api/tags).

### 2. Объяснение

Запрос: Объясни разницу между процессом и потоком в операционной системе. Дай три отличия и один короткий пример. Ответь по-русски.

Время: 10.03 с. Выход: 501 токенов.

Ответ модели (без исправлений):

Процесс и поток — это два основных концепта в операционных системах, но они имеют разные уровни абстракции и функциональности.

1. **Контроль над ресурсами**: Процесс обычно управляет большими блоками ресурсов, такими как память, файловые дескрипторы и устройства. Потоки, с другой стороны, обычно имеют более ограниченный доступ к ресурсам и могут быть созданы внутри процесса для выполнения конкретных задач. Например, в многопоточном приложении потоки могут использоваться для параллельной обработки данных, но они не могут свободно обращаться к памяти, которая доступна всему процессу.

2. **Создание и управление**: Создание процесса требует больше ресурсов и времени по сравнению с созданием потока. Процесс обычно требует загрузки полной копии кода и данных, в то время как поток может быть создан и управляем внутри уже существующего процесса. Например, при запуске программы, операционная система создает новый процесс, который затем может создать несколько потоков для параллельной обработки.

3. **Синхронизация и взаимодействие**: Потоки внутри одного процесса могут легко взаимодействовать друг с другом, так как они имеют доступ к общим ресурсам и могут легко общаться через каналы или другие механизмы синхронизации. Процессы же взаимодействуют друг с другом через механизмы межпроцессного взаимодействия (IPC), такие как очереди сообщений или сокеты, что требует больше усилий и ресурсов.

**Пример**: Представьте, что у вас есть приложение, которое параллельно обрабатывает данные из нескольких файлов. Вы можете создать процесс для каждого файла, что позволит вам эффективно использовать многоядерные процессоры. Внутри каждого процесса вы можете создать потоки для параллельной обработки данных из каждого файла, что позволит вам использовать все доступные ресурсы процессора для обработки данных.

### 3. Код и логика

Запрос: Напиши функцию uniqueStable(items) на Python: удали повторы, сохрани порядок первого появления, не меняй исходный список. Элементы хешируемые. Покажи результат для [3, 1, 3, 2, 1] и объясни сложность по времени и памяти. Ответь по-русски.

Время: 6.5 с. Выход: 321 токенов.

Ответ модели (без исправлений):

Конечно! Вот функция `uniqueStable(items)`, которая удаляет повторы из списка, сохраняя порядок первого появления элементов и не изменяя исходный список:

```python
def uniqueStable(items):
    seen = set()
    result = []
    for item in items:
        if item not in seen:
            seen.add(item)
            result.append(item)
    return result

# Пример использования
items = [3, 1, 3, 2, 1]
print(uniqueStable(items))  # Вывод: [3, 1, 2]
```

### Результат для `[3, 1, 3, 2, 1]`:
```
[3, 1, 2]
```

### Сложность:
- **Сложность по времени**: О(n), где n — длина входного списка `items`. Мы проходим по списку один раз, проверяя наличие элемента в множестве `seen`, что занимает константное время для каждого элемента.
- **Сложность по памяти**: О(m), где m — количество уникальных элементов в списке `items`. В худшем случае, если все элементы уникальны, множество `seen` будет содержать все элементы входного списка.

Эта функция эффективно решает задачу, сохраняя порядок первого появления элементов и не изменяя исходный список.

## Оценка

- Арифметика: правильный ответ `42`.
- Объяснение: модель отвечает связно, но ошибочно утверждает, что потоки не могут свободно обращаться к памяти всего процесса. Потоки одного процесса разделяют адресное пространство; ответ нельзя считать полностью правильным. Это ограничение качества модели, а не ошибка подключения.
- Код: алгоритм с `set` и списком сохраняет порядок, не изменяет вход; результат `[3, 1, 2]` правильный. Временная сложность O(n) — ожидаемая при среднем O(1) для операций множества, а не безусловная гарантия худшего случая.
- Дополнительно в браузере: `17 + 25` → `42`; «Умножь предыдущий результат на два» → `84`. Это проверка передачи истории.
