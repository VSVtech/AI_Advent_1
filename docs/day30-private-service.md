# День 30 — локальная LLM как приватный сервис

11 октября 2026 сервис развёрнут на существующем VPS проекта, рядом с MCP.
Это отдельный веб-чат и HTTP API: генерация полностью на VPS, без DeepSeek,
облачных моделей, RAG и внешних инструментов. Основное приложение и его RAG
продолжают работать по прежней схеме.

## Сервер и модель

Ubuntu 24.04.4, x86_64, 1 vCPU, 1902 MiB RAM, без GPU и swap. На момент
установки свободно около 25 GiB диска. Установлены Ollama **0.40.3** и
**Qwen2.5 0.5B Q4_K_M** (`qwen2.5:0.5b`, 397 821 319 байт весов).
Digest модели: `a8b0c51577010a279d933d14c2a8ab4b268079d44c5c8830c0a93900f1827c67`.

Модели 7B/27B из предыдущих занятий не помещаются в RAM этого VPS. Маленькая
0.5B позволяет проверить развёртывание и ограничения, но заметно уступает им
по качеству. Ниже сохранены её реальные ошибки, а не только успешные примеры.

## Как подключиться с Mac

Из корня проекта:

```bash
pnpm private:tunnel user@VPS_IP
```

Второй аргумент — необязательный путь к SSH-ключу; по умолчанию
`~/.ssh/ai-vps-key`. Укажите тот же адрес VPS, который используется для MCP
в `start.sh`. Скрипт получает API-ключ по SSH в
`.local-data/private-llm/token` с правами 0600, не выводя его в терминал,
и открывает туннель `127.0.0.1:18804 → VPS:127.0.0.1:18804`.
Для получения ключа нужен действующий SSH-доступ и `sudo -n` на VPS.

Держите терминал открытым. Откройте **http://127.0.0.1:18804**.
В другом терминале скопируйте ключ в буфер обмена:

```bash
pbcopy < .local-data/private-llm/token
```

Вставьте в поле «Ключ доступа» и нажмите «Подключиться».
Порт уже занят — проверьте, не открыт ли этот туннель в другом терминале.
После сна компьютера/обрыва сети при необходимости перезапустите команду.

В чате доступны история текущего диалога, новый диалог, остановка генерации,
выход, время ответа и число токенов. Скролл проходит по всей странице.
Ключ и сообщения живут только в памяти вкладки; обновление страницы очищает их.
При ошибке вопрос возвращается в поле ввода, в историю не попадает незавершённый ответ.

## HTTP API

- `GET /healthz` — жив ли процесс; не проверяет доступность модели.
- `GET /api/status` — модель, ограничения и активные генерации; нужен Bearer-ключ.
- `POST /api/chat` — история `messages` и необязательные `temperature`,
  `context_tokens`, `max_tokens`; нужен Bearer-ключ.

Пример без вывода ключа и без передачи его в аргументах процесса curl:

```bash
node --input-type=module <<'JS'
import { readFile } from 'node:fs/promises';
const key = (await readFile('.local-data/private-llm/token', 'utf8')).trim();
const response = await fetch('http://127.0.0.1:18804/api/chat', {
  method: 'POST',
  headers: { Authorization: `Bearer ${key}`, 'Content-Type': 'application/json' },
  body: JSON.stringify({
    messages: [{ role: 'user', content: 'Привет! Представься одним предложением.' }],
    temperature: 0,
    max_tokens: 128,
  }),
});
console.log(response.status, await response.json());
JS
```

Ответ содержит `message.content`, `model`, `finishReason`, `usage`, `seconds`,
`queueWaitSeconds` и `generationSeconds`. Время ожидания очереди отделено от
времени генерации. `/api/status` показывает `active`, `queued` и ёмкость очереди.
`finishReason: "length"` означает обрезание по лимиту и показывается в UI.
Историю передаёт клиент: user/assistant по очереди, последнее сообщение — user.
Выбор произвольной модели, system-сообщения и управляющие ручки Ollama закрыты.

## Ограничения и приватность

| Ограничение               | Значение                                                         |
| ------------------------- | ---------------------------------------------------------------- |
| Контекст модели           | максимум 2048 токенов                                            |
| Ответ                     | по умолчанию и максимум 256 токенов                              |
| Temperature               | по умолчанию 0; допускается 0–2                                  |
| История                   | максимум 24 сообщения                                            |
| Размер HTTP-тела          | 64 KiB                                                           |
| Частота                   | 8 авторизованных попыток `/api/chat` в минуту, общий лимит ключа |
| Одновременные генерации   | 1; остальные запросы ожидают FIFO-очередь                        |
| Очередь ожидания          | 4 места, без учёта активной генерации                            |
| Таймаут очереди           | 120 секунд, отдельно от таймаута модели                          |
| Таймаут модели            | 120 секунд                                                       |
| Лимиты systemd для Ollama | 1200 MiB RAM, 75% одного CPU                                     |
| Лимит systemd для API     | 192 MiB RAM                                                      |

Rate limit — фиксированное окно одного процесса. Ошибочные и принятые в очередь запросы
тоже расходуют квоту; перезапуск API сбрасывает счётчик. Возвращается
`Retry-After`. Это сервис для одного владельца/общего ключа, без пользовательских
аккаунтов и распределённого лимитера.

Несколько одновременных запросов принимаются в **ограниченную FIFO-очередь**.
Место в ней выделяется после чтения и проверки тела. Следующий запрос получает
модель после завершения предыдущего, включая ошибку или отмену. Отключение
клиента удаляет ожидающий запрос, он не запускается позднее. По истечении срока
ожидания возвращается `504 queue_timeout`. Только заполненная очередь даёт
`429 queue_full`; обычная занятость модели больше не вызывает отказа.
Rate limit ограничивает частоту независимо от очереди.

Очередь находится в RAM и не переживает рестарт процесса: клиенту нужно повторить
прерванный запрос. Порядок FIFO определяется завершением валидации запросов.
Параметры: `PRIVATE_LLM_QUEUE_CAPACITY=4`, `PRIVATE_LLM_QUEUE_TIMEOUT_MS=120000`.
В чате показывается общая загрузка сервера; это не персональная позиция запроса.

До инференса применяется **консервативная оценка входа**: число UTF-8-байт,
32 единицы на каждое сообщение, 256 на обрамление и резерв всего ответа.
Это не точный токенизатор; русский текст может быть отклонён раньше реального
предела. История не обрезается молча — возвращается `413 context_limit`.
Параметр `num_ctx` дополнительно передаётся самой Ollama.

API слушает только `127.0.0.1:18804`, Ollama — `127.0.0.1:11435` на VPS.
Передача по сети шифруется SSH; HTTP используется внутри туннеля. Доступ
проверяют SSH-ключ и отдельный случайный 256-битный ключ API. Секреты не включены
в Git. Заголовки Host/Origin проверяются, CORS не открыт, UI выводит ответы как
текст. На диске сервис не сохраняет историю, в журнал API пишет только статус
и время запроса. У администратора VPS остаётся доступ к процессам и памяти.

`OLLAMA_NO_CLOUD=1` отключает облачные функции. API перед каждым запросом
проверяет, что выбранная модель установлена локально и не является облачным
алиасом. Скачивание программы и весов требует сети; генерация не обращается
к внешнему провайдеру. API-unit дополнительно ограничен loopback-адресами.

## Развёртывание и обслуживание

Код сервиса не требует npm-зависимостей, работает на Node.js 22.13+;
на VPS используется копия уже установленного Node.js 24.21.0.
Конфигурации лежат в `deploy/private-llm/`.

1. Передайте `scripts/private-llm/` и `deploy/private-llm/` на VPS, сохранив
   структуру каталогов. Не копируйте `.env.local`, SSH-ключи и документы RAG.
2. Скачайте официальный архив
   `https://github.com/ollama/ollama/releases/download/v0.40.3/ollama-linux-amd64.tar.zst`.
3. Запустите на VPS:

```bash
sudo bash SOURCE/deploy/private-llm/install.sh \
  /absolute/path/to/SOURCE \
  /absolute/path/to/node \
  /absolute/path/to/ollama-linux-amd64.tar.zst
```

Установщик проверяет SHA-256 архива, создаёт отдельного системного пользователя
`ai-llm`, устанавливает runtime и UI, генерирует ключ, скачивает модель и включает
два systemd-unit. Повторная установка сохраняет ключ и настройки.
Профиль рассчитан на CPU x86_64; для другой архитектуры нужен другой архив.

| Назначение           | Путь на VPS                                    |
| -------------------- | ---------------------------------------------- |
| Runtime и приложение | `/opt/ai-private-llm/`                         |
| Веса модели          | `/var/lib/ai-private-llm/models/`              |
| Конфигурация API     | `/etc/ai-private-llm/service.env`              |
| Ключ                 | `/etc/ai-private-llm/token`, root:ai-llm, 0640 |

```bash
sudo systemctl status ai-private-ollama ai-private-llm
sudo journalctl -u ai-private-llm -n 30 --no-pager
sudo systemctl restart ai-private-llm
sudo systemctl show ai-private-ollama -p MemoryCurrent -p MemoryPeak -p NRestarts
```

Числовые ограничения меняются в `service.env`, затем перезапускается API.
При замене модели сначала скачайте её через локальный Ollama-порт 11435 и
согласуйте её память/окно с лимитами Ollama-unit. Существующий MCP не менялся.

Отключить сервис, сохранив веса и настройки:

```bash
sudo systemctl disable --now ai-private-llm ai-private-ollama
```

Снимки `/api/status` подтверждают одну активную генерацию; ещё два запроса
ожидали в очереди. Порядок и отсутствие одновременных обращений к модели также
проверены HTTP-тестом с управляемым генератором. Корректность содержания этих
ответов не входит в критерий завершения запросов.

Прежняя проверка «один ответ + два 429 busy» проверяла отказ при перегрузке.
Она заменена проверкой успешного обслуживания всех трёх запросов. Rate limit
и его восстановление проверяются отдельно. Это короткий прогон, не SLA.

Пик cgroup-памяти Ollama в измерениях — около 1,02 GiB. Cgroup учитывает файловый
кэш, не только веса. Точные текущие показатели сохранены в JSON-отчёте; API и MCP
остались активны, автоматических перезапусков не было.

**Качество отдельно от доступности:**

- `17 + 25` → **«32»**, ошибка; ожидалось 42.
- Удалить повторы из `[3, 1, 3, 2, 1]`, сохранив порядок → **`[1, 3, 2]`**,
  ошибка; ожидалось `[3, 1, 2]`.
- Объяснение HTTP API — в целом по теме, но модель нарушила просьбу ограничиться
  двумя предложениями. Нельзя считать это полностью выполненной инструкцией.

Скрипт проверяет доступность, завершение и ограничения. Поля
`answerMatchesExpected` отмечают ошибки в двух однозначных задачах и не влияют
на оценку транспортной стабильности. Для практической замены локальной 7B
этот VPS и модель слишком слабы.

В настоящем браузере также проверены вход, два последовательных сообщения,
выход и мобильная ширина 390 px. Модель сохранила название проекта «Север» во
втором ответе. JS-ошибок и горизонтального переполнения нет; при выходе история
очищается. Скриншоты и сырые логи лежат локально в `.local-data/day30/`.

Проверки кода: **576/576 тестов**, TypeScript, oxlint и production-сборка.
Отдельные тесты покрывают авторизацию, запрет внешнего upstream/облачных моделей,
лимиты тела и контекста, rate limit, FIFO-порядок, переполнение очереди, отмену ожидающих запросов и таймауты.
