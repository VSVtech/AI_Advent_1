# DeepSeek Chat

Локальный менеджер агентов для диалога с DeepSeek через Responses API.
API-токен используется только серверными маршрутами и не передаётся в
браузер. Слева — список запущенных агентов и кнопка «Новый агент»; справа —
диалог с выбранным агентом или экран настройки нового. История каждого
агента, его настройки и выбранная сессия сохраняются в локальном хранилище
браузера и восстанавливаются после обновления, закрытия или повторного открытия
вкладки на том же устройстве. Полная история всегда остаётся в интерфейсе и
локальном хранилище. При создании агента выбирается один из четырёх режимов
контекста: без сжатия, Sliding Window, Sticky Facts или Branching. Выбор влияет
на запросы к DeepSeek, но не удаляет историю из интерфейса.

## Агент как отдельная сущность

Требование задания — реализовать агента как отдельную сущность, а не один
вызов API: логика запроса и ответа инкапсулирована в классе `Agent`
(`lib/agent.ts`), а не размазана по UI-компонентам.

- `Agent` хранит собственную конфигурацию (модель, температуру, формат
  ответа, целевую длину, лимит и стратегию контекста, режим системного промпта,
  способ выбора профиля) и
  собственную историю сообщений — каждый агент независим от остальных.
- `Agent.sendMessage(content)` — единственная точка входа для отправки
  запроса. Метод сам строит тело запроса, вызывает `POST /api/chat`,
  разбирает потоковый ответ (`readChatStream`), обновляет историю по мере
  поступления токенов и обрабатывает отмену (`stop()`) и ошибки. UI-компоненты
  никогда не вызывают `fetch` напрямую.
- Состояние агента наружу отдаётся через простой паттерн
  `subscribe`/`getSnapshot` (без хранения его в React state), а
  `hooks/use-agent.ts` подписывает компонент на изменения через
  `useSyncExternalStore`, чтобы чат перерисовывался при каждой дельте ответа.
- `Agent.stop()` прерывает текущий запрос, `Agent.clearHistory()` очищает
  диалог, `Agent.dispose()` останавливает агента и отписывает всех слушателей
  (вызывается при удалении агента или размонтировании страницы).
- Сессии сохраняются в `localStorage` в версионированном формате. Повреждённые
  записи игнорируются, а незавершённый поток после перезапуска помечается как
  остановленный.
- Управление контекстом также принадлежит `Agent`: он ограничивает историю для
  API и создаёт независимые ветки. Отдельный `MemoryCurator` после каждого
  сообщения пользователя анализирует недавний диалог через LLM и обновляет
  факты текущего диалога и общую долговременную память. Полная
  история каждой ветки остаётся доступна UI после перезапуска.
- `Agent.mergeBranches(firstId, secondId)` суммаризирует каждую выбранную ветку
  отдельными запросами, затем объединяет две сводки ещё одним запросом.
  Итоговое summary сохраняется в новой ветке и подставляется в её будущие
  запросы; исходные ветки и их истории не меняются.
- Тесты в `tests/agent.test.ts` проверяют построение запроса, обработку
  потоковых дельт, накопление токенов, отмену (с частичным и пустым ответом),
  сетевые и API-ошибки, а также подписку/отписку слушателей.

## Три слоя памяти

Правая панель «Память» показывает две вкладки: «Сессионная» (автоматически
извлечённые факты текущего диалога, рабочие записи и сводка ветки при
наличии) и «Долговременная» (общие записи всех агентов). История сообщений
отображается отдельно в чате и не является краткосрочной памятью. На узком экране
панель открывается кнопкой справа в шапке чата. Кнопка «Изменить» открывает
форму сохранения и удаления записей.
Рабочие записи пользователь добавляет вручную. Долговременные записи
анализатор выбирает автоматически; их также можно добавить или удалить
вручную. Повторный ключ обновляет запись. У долговременной записи есть тип:
профиль, решение или знание.

У каждой записи в правой панели есть кнопка удаления с подтверждением.
Краткосрочный факт можно перенести в долговременную память: выбрать тип
записи, подтвердить перенос, после чего он исчезнет из краткосрочной памяти и
станет общим для всех агентов. Если ключ уже существует в общей памяти,
подтверждение показывает, какое значение будет заменено. Если сохранение не
удалось, исходный факт остаётся на месте. После удаления или переноса старые
реплики этой сессии не анализируются повторно, чтобы факт не появился обратно
из её истории.

| Слой           | Что хранится                                                                                      | Куда передаётся модели                                                  |
| -------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Краткосрочная  | Автоматически извлечённые факты текущего диалога; в Branching — отдельно для каждой ветки         | В первое сообщение `input`; Sliding Window намеренно их не подставляет  |
| Рабочая        | Явно сохранённые ключи-значения текущей задачи; в Branching — отдельно для каждой ветки           | В то же первое сообщение `input`                                        |
| Долговременная | Отобранные анализатором или сохранённые вручную профиль, решения и знания; общие для всех агентов | В системные `instructions`, отдельно от истории и сессионного сообщения |

В JSON сессии история и слои лежат отдельно: `agents[].messages`,
`agents[].facts` (краткосрочные факты), `agents[].memoryLayers.working` и
общий верхнеуровневый `longTermMemory`. Все восстанавливаются из локального
хранилища браузера после перезапуска.
Старые личные долговременные записи агентов при первом открытии объединяются
в общую память; если одинаковый ключ имел разные значения, в названии
дополнительной записи сохраняется имя исходного агента. «Очистить историю диалога»
удаляет историю и краткосрочные факты, но не рабочие и долговременные записи.
При создании двух веток рабочая и краткосрочная память копируется в каждую и
далее меняется независимо. При объединении рабочие записи каждой
ветки учитываются в её сводке; новая объединённая ветка начинает с пустой
рабочей памятью, а долговременная остаётся общей для всех агентов. Удаление
агента не удаляет общую память. Если вызов анализатора памяти не удался,
существующие факты сохраняются, а основной агент всё равно отвечает. Анализатор
нормализует отдельные неверно типизированные факты и один раз повторяет запрос,
если не получил распознаваемый краткосрочный слой.

Перед запросом агент добавляет сессионную память отдельным сообщением в начале
`input`, а долговременную — в системные `instructions`. Профиль также попадает
в `instructions`: после обычного промпта и перед долговременной памятью. Даже
если обычный системный промпт отключён, непустой профиль или долговременная
память всё равно создают `instructions` с доступными данными. В режимах без
сжатия, Sticky Facts и
Branching сессионное сообщение содержит и краткосрочные факты; при Sliding
Window — только рабочие записи.
Последнее сообщение пользователя важнее памяти, а при конфликте рабочих и
долговременных данных приоритет у данных текущей задачи. Например, если в
долговременном профиле сохранён язык «Русский», а в рабочей памяти дедлайн
«Пятница», оба факта доступны модели даже при Sliding Window, когда ранние
сообщения уже не отправляются. Память хранится на этом устройстве в
`localStorage` и не предназначена для секретов.

## General Profile

На отдельной странице [General Profile](http://localhost:3000/general-profile)
можно написать общий профиль свободным текстом: сведения о себе, стиль и формат
ответов, ограничения. Он сохраняется в браузере отдельно от сессий агентов.
Ссылка на страницу есть в левом меню. Пустой текст означает отсутствие профиля.

При создании агента галочка «Использовать стандартный профиль» включена по
умолчанию. Такой агент берёт актуальный текст General Profile при **каждом**
запросе, поэтому изменения страницы действуют и на уже созданных агентов.
Если снять галочку, появится поле собственного профиля, которое сохраняется в
настройках конкретного агента; пустое поле не добавляет профиль в запрос.
Сессии старой версии без этой настройки восстанавливаются без профиля, чтобы
не менять их поведение неожиданно.

Порядок системных инструкций: промпт агента → профиль → долговременная память.
Краткосрочная и рабочая память остаются в начале `input`. При конфликте агент
ориентируется на последнее явное сообщение пользователя, затем на память
текущего контекста, затем на профиль. Предпочтительный формат профиля не
отменяет технически заданный JSON, XML или YAML.

## Состояние задачи (Task State Machine)

Под кнопкой «Новый агент» находится «Создать задачу». На первом экране задаются
название и цель. Для каждой задачи создаётся отдельный диалог со стандартными
настройками агента; обычные чаты не получают панель состояния задачи. Задачи
отображаются отдельным списком в боковой панели.

Задача начинается на этапе `planning`. Текущий шаг — это сам активный этап,
без отдельного редактируемого поля. Допустимые переходы заданы явно: вперёд
`planning → execution → validation → done`, назад — только на один соседний
этап (`done → validation → execution → planning`). Перескочить этап нельзя.
На экране задачи видны цель,
активный этап и ожидаемое действие. После ответа основная LLM сама формулирует
ожидаемое действие по цели и текущему результату. Когда результат этапа готов,
она предлагает в ответе переход к следующему этапу. Предложение сохраняется
в состоянии задачи, но само по себе этап не меняет. Пользователь явно принимает
результат ответом в чате своими словами, без фиксированной фразы; только тогда автомат
переходит к следующему этапу и передаёт подтверждение в LLM. Просьба начать
следующий этап без предложения и принятия результата не переключает автомат.
Очевидные подтверждения распознаются локально; для иных формулировок отдельный
короткий запрос к LLM проверяет смысл ответа. Отказ, просьба о правках и
неясный ответ не меняют этап. Если эта проверка недоступна, переход не происходит.
После предложения можно ответить и коротким названием следующего этапа,
например `done` после `validation`, либо коротким «давай». Предложение распознаётся даже в одной строке
с ожидаемым действием. Сохранённые диалоги с таким ранее пропущенным
подтверждением восстанавливаются при открытии задачи. Слова модели «задача
завершена» на этапе `validation` сами не меняют состояние: требуется ответ
пользователя.
Если модель не вывела техническую строку перехода, но в ожидаемом действии
прямо попросила принять результат текущего этапа (например, подтвердить план),
это тоже считается предложением. После явного подтверждения пользователя
переход происходит до следующего запроса к модели. Подтверждение, отправленное
перед неудачным ответом API, восстанавливается из сохранённого диалога.
Кнопки смены этапа и прежняя команда `/этап` больше не используются.

Если на текущем этапе обнаружилась ошибка результата предыдущего (например,
на `execution` план оказался невыполнимым), агент не исправляет прошлый этап
«на месте»: объясняет проблему и предлагает откат на один этап. Откат тоже
требует отдельного подтверждения пользователем в чате. После возврата прежнее
утверждение результата считается недействительным: результат исправляют на
соответствующем этапе и заново подтверждают перед переходом вперёд. Это
работает и для `validation → execution`, и для `done → validation`.

На любом этапе доступна пауза, в том числе во время генерации ответа — текущий
запрос прерывается. Пока задача на паузе, новые сообщения не отправляются в
DeepSeek. Кнопка «Продолжить задачу» возвращает к тому же этапу и
ожидаемому действию. Состояние хранится отдельно от истории диалога в локальном
хранилище браузера и восстанавливается после перезапуска приложения. Название,
цель и активное состояние передаются отдельно от истории в системных
инструкциях модели, даже при выключенном обычном системном промпте и Sliding
Window. Текущий этап имеет приоритет над противоречащими описаниями в чате и
памяти, поэтому после возобновления не нужно повторно объяснять задачу.
Очистка истории чата состояние задачи не удаляет.

Диалог задачи пополняет память так же, как обычный чат. Для задач анализ
запускается после ответа LLM и получает сообщения пользователя и ответы
ассистента. Технические инструкции с названием, целью и состоянием задачи
подставляются только в запрос к основной модели, но не передаются агенту
памяти. Служебная команда кнопки «Попросить агента составить план» помечается
отдельно, исключается из анализа памяти и не повторяется в запросах после
первого ответа. Подтверждение пользователя в чате, напротив, входит в обычную
историю и анализ памяти. После перехода к выполнению модель получает явное указание,
что подтверждение уже получено. API дополнительно подставляет перед текущим
запросом служебное сообщение о подтверждённом этапе: оно не показывается в
чате и не сохраняется в память, но не даёт прежним ответам о планировании
заблокировать выполнение. Переходы автомата из памяти не восстанавливаются:
ответы модели могут предложить следующий этап, но не подтвердить его.
Ответ задачи проверяется сервером на соответствие активному этапу и инвариантам
до показа пользователю. Нарушающий ответ не показывается: сервер пробует
перегенерировать его с объяснением ошибки; при неудаче возвращает ошибку.

При первом открытии этой версии приложение однократно удаляет сохранённые
ранее чаты, задачи, агентов и память (`agent-sessions:v1`) по запросу
пользователя. `General Profile` хранится отдельно и не затрагивается.

В режиме Branching новые ветки получают копию состояния текущей задачи, если
ветвление выполнено от последнего сообщения. Затем состояние меняется в каждой
ветке независимо. При объединении веток новая ветка начинает без состояния:
противоречивые состояния исходных веток не объявляются автоматически согласованными.

## Инварианты задачи

При создании задачи можно добавить до 20 инвариантов (архитектура, стек,
решения, бизнес-правила) и удалить любой из списка до создания. Изначально
список пуст. После создания инварианты показываются на экране задачи и
сохраняются вместе с её состоянием отдельно от диалога и памяти. Сообщения в
чате не редактируют этот список.

Инварианты передаются в системных инструкциях каждого запроса задачи, даже
если обычный системный промпт выключен. При конфликте ассистент должен назвать
ограничение, объяснить отказ и предложить совместимый вариант. Для задачи с
инвариантами сервер сначала получает полный ответ, затем отдельным запросом к
LLM проверяет его по списку. Нарушающий ответ не показывается: сервер до двух
раз повторяет генерацию с указанием конкретного нарушения. Если исправленный
ответ не получен, в текстовом режиме показывается безопасный отказ, а в
структурированном — ошибка с объяснением конфликта. Если проверка недоступна,
непроверенный ответ не выдаётся. Токены дополнительных вызовов для проверки
и исправления отображаются отдельно. Без инвариантов обычная потоковая выдача
остаётся прежней. Семантическая проверка LLM снижает риск, но не является
формальным доказательством соблюдения произвольных правил.

## Экран «Новый агент»

Кнопка «Новый агент» в сайдбаре открывает форму настройки
(`components/agent-setup.tsx`) с теми же параметрами, что раньше были на
вкладке «Чат»:

- **Модель** — список запрашивается с сервера (`GET /api/models`, который
  вызывает `GET https://api.deepseek.com/models` тем же API-токеном) —
  показываются только модели, реально доступные по текущему токену, а не
  жёстко зашитый список. Если запрос не удался или токен не настроен,
  доступной остаётся только модель по умолчанию (`deepseek-v4-flash`).
- **Температура** — от 0 до 2 (шаг 0,1, по умолчанию 1).
- **Формат ответа** — Text, JSON, XML или YAML. Структурированные ответы
  проверяются на сервере и выводятся с подсветкой синтаксиса; при ошибке
  выполняется не более трёх повторных запросов к модели.
- **Целевая длина ответа** — передаётся модели как диапазон 87,5–112,5% от
  указанного значения (не превышая технический максимум). Технический
  `max_output_tokens` рассчитывается как цель плюс 20%, но запас не может
  быть меньше 500 или больше 2000 токенов — это оставляет место для
  завершения и закрытия структурированных форматов.
- **Лимит контекстного окна** — по умолчанию равен реальному окну модели в
  1 000 000 токенов. Его можно искусственно уменьшить, например до 2000,
  чтобы быстро воспроизвести переполнение. Перед вызовом DeepSeek сервер
  оценивает токены всей истории и системного промпта и возвращает отдельную
  ошибку `context_window_exceeded`, если лимит превышен. После ответа агент
  сверяет лимит с точным `input_tokens` из API: если предварительная оценка
  пропустила переполнение, ответ сохраняется с предупреждением. Следующий
  запрос блокируется в режимах без сжатия и Branching; Sliding Window и Sticky
  Facts могут сформировать более короткий следующий запрос.
- **Управление контекстом** — четыре взаимоисключающих режима. «Без сжатия»
  отправляет всю историю. Sliding Window отправляет последние 10 сообщений.
  Sticky Facts отправляет последние 10 сообщений вместе с автоматически
  извлечёнными краткосрочными фактами. Sliding Window факты хранит, но не
  подставляет — так его контекст действительно остаётся скользящим окном.
  Branching создаёт две ветки от последнего ответа или от выбранного checkpoint.
  Их можно вести независимо и переключаться между ними; в запрос отправляется
  только история выбранной ветки. Текущую ветку можно объединить с выбранной
  второй: агент показывает единое summary и открывает новую ветку для продолжения.
  В каждом режиме история сохраняется для интерфейса.
  Отдельный анализатор памяти делает дополнительный вызов LLM на каждое
  сообщение пользователя в любом режиме;
  Слияние делает как минимум три дополнительных вызова LLM (больше для длинных
  веток). Branching не ограничивает длину отдельной ветки и не предотвращает её
  переполнение.
- **Системный промпт** — тот же контрол, что и раньше (`SystemPromptControl`):
  можно использовать промпт, собранный из формата и целевой длины, написать
  свой (1–20 000 символов) или отключить эти дополнительные инструкции.
  Долговременная память в `instructions` остаётся и при выключенном контроле.
- **Профиль** — общий профиль со страницы General Profile либо собственный
  текст агента. Если выбранный текст пуст, профиль не добавляется. Непустой
  профиль остаётся в `instructions`, даже когда обычный системный промпт выключен.

Все параметры, включая выбор режима профиля и собственный текст, фиксируются при
создании агента. Общий профиль можно обновлять отдельно в любое время. Форма не
даёт создать агента с недопустимой температурой, целевой длиной или пустым
кастомным системным промптом.

## Список агентов

Каждый агент в списке слева показывает своё имя (по умолчанию — «Агент ·
<Модель>», можно задать своё при создании), модель и индикатор активной
генерации. Клик по агенту открывает его диалог, кнопка-корзина у пункта
списка удаляет агента вместе с его историей (`Agent.dispose()`). В шапке
диалога — те же кнопка очистки истории и бейджик модели, но модель и лимит
контекста у агента фиксированы и не могут быть изменены без создания нового
агента. Под каждым ответом показывается использование окна, поэтому рост
контекста можно сравнивать по мере продолжения диалога.

## Подключение MCP (день 16)

Отдельный [минимальный пример](scripts/mcp/README.md) поднимает MCP-сервер с
инструментами `ping`, `server_time` и `get_weather`. Клиент использует MCP SDK,
устанавливает соединение и выводит список `name`, `description`, `inputSchema`. Сервер
слушает только `127.0.0.1`, поэтому для удалённой капсулы доступен через
SSH-туннель. При сообщении агент получает список доступных инструментов,
передаёт их модели как функции, выполняет выбранный вызов через MCP и возвращает
результат модели для окончательного ответа. Модели доступны только
инструменты из списка разрешённых для каждого сервера в
[mcp-config.ts](lib/server/mcp-config.ts); если MCP недоступен, обычный чат
продолжает работать без них. Ответ с доступными MCP-инструментами приходит
после завершения вызовов, без посимвольной потоковой выдачи.

Кнопка «MCP Инструменты» под «Новый агент» показывает актуальные инструменты
капсулы и статус подключения. Для локального чата откройте
[SSH-туннель](scripts/mcp/README.md) к капсуле; публичный MCP-порт не нужен.

## Планировщик погоды через MCP (день 18)

MCP-сервер капсулы получил два инструмента с отложенным выполнением.
`schedule_weather_collection` ставит задание «замер каждые N минут в течение
M минут» и возвращает его id. `get_weather_summary` возвращает агрегированный
результат: для задания — фактические замеры, диапазон температур и признак
дождя, без аргументов — последнюю суточную сводку по Москве.

Расписание выполняет cron на капсуле. Раз в минуту он запускает
`scripts/mcp/weather-tick.mjs`: скрипт вызывает MCP-инструмент `get_weather`,
сохраняет замеры в JSON и делает то, что пора, — ежечасный замер для Москвы,
суточную сводку в 16:00 МСК и замеры активных заданий. Капсула работает
круглосуточно, поэтому сбор не зависит от того, открыт ли чат и включён ли
компьютер.

Агенту достаточно написать, например: «Собирай данные о погоде каждые 2 минуты в
течение 20 минут и дай сводную таблицу». Модель сама вызывает
`schedule_weather_collection`, а чат запоминает id задания. Пока вкладка открыта,
приложение раз в 10 секунд спрашивает `get_weather_summary` через `/api/weather`.
После окончания сбора в тот же чат приходят таблица фактических замеров и
короткий вывод модели; без ключа DeepSeek вместо вывода показывается вычисленный
итог. Если вкладку закрыть, результат придёт при следующем открытии. Последняя
суточная сводка видна в боковой панели и на экране «MCP Инструменты».

Ограничения задания: интервал 1–60 минут, длительность 2–120 минут, не более
61 замера и одно активное задание за раз. Первый замер делается в течение минуты
после запуска. Установка на капсулу описана в
[инструкции](scripts/mcp/README.md#планировщик-погоды-день-18).

## Композиция MCP-инструментов (день 19)

MCP-инструмент `find_concert` ищет по локальной захардкоженной афише, где и
когда выступает исполнитель. Исполнители — Смешарики, города — случайные
города Германии. Имена распознаются в любом падеже («где выступает Нюша»,
«концерт Кар-Карыча»). Если исполнителя нет в афише, инструмент возвращает
список тех, кто в ней есть.

Скилл агента «Погода на концерте» ([lib/agent-skills.ts](lib/agent-skills.ts))
связывает два MCP-инструмента в цепочку: сначала `find_concert` получает
город, затем `get_weather` запрашивает погоду ровно в этом городе. Скилл
передаётся модели вместе с описаниями инструментов и только тогда, когда оба
инструмента есть на сервере. На вопрос «Какая погода, где выступает Нюша?»
агент сам вызывает оба инструмента по очереди, а под ответом видно
`MCP: find_concert, get_weather`. Список скиллов и готовность их цепочек
показаны на экране «MCP Инструменты».

Города в афише подобраны так, чтобы геокодер Open-Meteo находил их именно в
Германии: например, «Гейдельберг» он находит в ЮАР, а «Фрайбург» — в деревне.
Ту же цепочку без модели выполняет `pnpm mcp:concert-weather -- Нюша`.

## Оркестрация нескольких MCP-серверов (день 20)

Агент подключён к трём MCP-серверам из реестра
[mcp-config.ts](lib/server/mcp-config.ts):

- **MCP на капсуле** (VPS, через SSH-туннель) — погода, афиша, планировщик;
- **Поездки** (`scripts/mcp-servers/travel.mjs`, порт 18801) — `plan_trip`:
  расстояние, время на поезде, машине и самолёте и рекомендуемый вариант;
- **Заметки** (`scripts/mcp-servers/notes.mjs`, порт 18802) — `save_note`,
  `list_notes`, `read_note`: Markdown-файлы в `.local-data/notes`.

Локальные серверы поднимает `start.sh`. При каждом сообщении агент параллельно
подключается ко всем серверам и отдаёт модели общий список инструментов; в
описании каждого инструмента указан его сервер. Модель выбирает инструмент, а
маршрутизатор ([mcp-agent.ts](lib/server/mcp-agent.ts)) отправляет вызов
серверу-владельцу. Если одно имя инструмента есть на нескольких серверах, оно
получает префикс сервера (`ai-vps__ping`). Недоступный сервер пропускается,
остальные работают. За один ответ агент делает до 6 раундов и 12 вызовов
инструментов.

Под ответом показан порядок вызовов с серверами, например:
`MCP: ai-vps · find_concert → ai-vps · get_weather → travel · plan_trip → notes · save_note`.
Так выглядит длинный флоу скилла «Поездка на концерт» на запрос «Спланируй
поездку на концерт Нюши из Берлина и сохрани план в заметки». На экране
«MCP Инструменты» видны все три сервера, их статус и серверы каждого шага в
цепочках скиллов.

DeepSeek тарифицирует API-запросы отдельно. Токен не следует добавлять в Git или
в переменные с префиксом `NEXT_PUBLIC_`.

## Индексация документов (день 21)

«База знаний» в боковой панели показывает корпус, состояние локального индекса,
чанки с источниками и строками, проверочный поиск и сравнение стратегий. На этом
этапе дня 21 строится индекс; подключение к ответам реализовано в дне 22 ниже.

Корпус задаётся явным списком в `rag/corpus.json`: README, документация MCP и
исходники приложения. В отчёте сохраняются число файлов, символов и строк —
эквивалент требуемых 20–30 страниц в коде. Зависимости, сборка, `.env`, история
диалогов и локальные заметки в корпус не входят. Поддерживаются UTF-8 Markdown,
TXT и исходники TS/TSX/JS/MJS; PDF/OCR в эту версию не входят.

### Первый запуск

Установите [Ollama](https://ollama.com/download), затем в отдельных терминалах:

```bash
pnpm rag:ollama
```

```bash
pnpm rag:setup
pnpm rag:index
pnpm rag:compare
pnpm rag:search structure "Как сохраняется память агента?"
```

`rag:ollama` запускает локальный сервер на `127.0.0.1:11434` с моделями в
`.local-data/rag/models`; если есть `.local-data/rag/runtime/ollama`, использует
этот бинарный файл, иначе установленную команду `ollama`. Если Ollama уже
работает, повторно запускать сервер не нужно. `rag:setup` скачивает модель
`qwen3-embedding:0.6b` (около 639 МБ) и токенизатор Qwen с закреплённой ревизией
Hugging Face. После подготовки индексация и поиск работают локально без
DeepSeek API и без отправки документов наружу. URL Ollama можно переопределить
серверной переменной `RAG_OLLAMA_URL`.

Локальный сервис UI запускает `start.sh`; он также запускает доступную Ollama,
если сервер ещё не работает. При отдельном `pnpm dev` запустите
ещё `pnpm rag:server` (порт 18803, переменная `RAG_PORT`). Маршрут `/api/rag`
проксирует запросы к нему; при изменении порта задайте также `RAG_SERVICE_URL`.
Сервис слушает loopback, отклоняет браузерные Origin и посторонние Host.
Это локальный режим: для развёртывания приложения в облаке понадобится
доступный серверный сервис индексации и отдельная авторизация.

### Стратегии и формат индекса

- `fixed`: до 512 токенов, без пересечения, отдельно для каждого файла.
- `overlap`: до 512 токенов, пересечение 96 токенов (на границах Unicode может
  быть немного меньше, чтобы не разорвать символ).
- `structure`: Markdown по ATX-заголовкам вне fenced-блоков, код по объявлениям
  верхнего уровня через TypeScript AST. Короткие соседние блоки одного раздела
  объединяются; длинные разделы и классы дополнительно режутся до 512 токенов.
  Markdown Setext-заголовки и разбиение класса по методам пока не реализованы.

Каждый чанк содержит текст, embedding, `source`, `title`, `file`, `section`,
`chunk_id`, `document_id`, номер чанка, токены, стратегию, строки и смещения.
Смещения — индексы UTF-16 в тексте с нормализованными переводами строк LF.
ID зависит от источника, хеша текста, параметров и границ. Манифест хранит хеши
документов, ревизию токенизатора, digest модели, размерность и статистику.

Результаты лежат в `.local-data/rag/builds/<build_id>/`: `fixed.json`,
`overlap.json`, `structure.json`, `comparison.json` и `comparison.md`.
`current.json` указывает на последнюю полную сборку. Три индекса публикуются
атомарно; при ошибке остаётся прежняя версия. Кеш в `cache/` учитывает весь
текст и конфигурацию модели, включая её digest. Смена модели требует новой
индексации. Поиск — точный cosine similarity по нормализованным векторам.

Сравнение использует 20 ручных вопросов в `rag/questions.json` с фрагментами
ответов и хешами исходников. Попадание засчитывается, если один чанк полностью
содержит размеченный ответ. Отчёт показывает Hit@5, MRR@5, размеры чанков,
дублирование текста, размер файлов, время и кеш. Время включает прогрев и
кеширование, поэтому это не независимый benchmark скорости. После изменения
размеченного документа обновите хеш и смещения эталона по исходнику;
сравнение откажется использовать устаревшую разметку. Не подгоняйте эталоны
под результаты поиска. Тестовые эмбеддинги используются только в unit-тестах.

Если процесс индексации был принудительно завершён, проверьте, что он больше
не работает, затем удалите `.local-data/rag/build.lock`. Не удаляйте lock во
время работающей сборки. Индекс, модель и кеш игнорируются Git; команды выше
воспроизводят их из корпуса. Новые модули находятся в `scripts/rag/`, экран —
в `components/knowledge-base-view.tsx`.

## Первый RAG-запрос (день 22)

В настройках нового агента и над диалогом есть два режима: **Без RAG** и
**С RAG**. По умолчанию RAG выключен, в том числе у старых сохранённых агентов.
Выбор сохраняется вместе с агентом; во время генерации переключение запрещено.
У каждого нового ответа сохраняется фактический режим и, для RAG, снимок
переданных источников. Источники остаются доступны после перезапуска браузера.

Путь запроса: последний вопрос → локальная модель эмбеддингов → top-5 по
cosine similarity из индекса `overlap` → сообщение `RAG_CONTEXT_JSON` перед
вопросом → существующий DeepSeek Responses API. Стратегия с пересечением
выбрана по сравнению дня 21. Контекст ограничен 18 000 символов вместе с
метаданными; целые чанки, не помещающиеся в бюджет, пропускаются. Полный запрос
вместе с RAG проходит прежнюю проверку лимита контекста. Вопрос для поиска —
до 2000 символов; для сообщения с вложениями учитываются его текстовые части.

Модель получает правила отделять данные от инструкций, ссылаться на источники
как `[S1]`, `[S2]` и признавать недостаток сведений. Под ответом раскрывается
список реально переданных чанков с текстом, файлом, строками, score и версией
индекса. Это перечень контекста, а не доказательство корректности всех ссылок
модели. RAG добавляется только к основным ответам, а не к внутренней обработке
памяти и суммаризации. Поток, отмена, MCP, проверка инвариантов и структурированные
форматы сохраняются. Найденные фрагменты отправляются в DeepSeek; эмбеддинги
продолжают вычисляться локально.

Если сервис, модель или индекс недоступны, источники повреждены или фрагменты
отсутствуют, запрос завершается понятной ошибкой. Автоматического переключения
на обычный ответ нет. Переключение режима внутри диалога сохраняет историю:
предыдущие ответы с RAG могут влиять на последующие ответы без нового поиска.

Для чистого сравнения откройте **Сравнение RAG** в боковом меню или ссылку из
базы знаний: страница `/rag-comparison` содержит 10 вопросов. Каждый вопрос
показан общей строкой над тремя колонками: **Без RAG — С RAG — С RAG + обработка**. Кнопка
«Запустить 10 вопросов» последовательно проходит весь набор: на каждый вопрос
делает три отдельных API-запроса с одинаковой моделью,
температурой 0, инструкциями и лимитом 1400 выходных токенов. История, профиль,
память и MCP в этом эксперименте выключены. Эталоны модели не передаются.
Девять вопросов проверяют факты проекта; десятый — отказ выдумывать неизвестные
параметры PostgreSQL. Точный список: `rag/answer-questions.json`.

Ответы появляются в таблице по мере генерации, под ответом с RAG раскрываются
переданные источники. Ожидания и допустимые источники остаются в наборе
`rag/answer-questions.json`. Ответы сохраняются в localStorage
этого браузера; незавершённые ответы после перезагрузки помечаются остановленными.
«Остановить» отменяет активные запросы и очередь, сохраняя полученный текст;
уход со страницы также останавливает запросы. Ошибка отдельного ответа не мешает
остальным вопросам. Новый запуск заменяет прежние ответы.
Индекс фиксируется на весь прогон. «Загрузить отчёт из CLI» заполняет таблицу
результатами `pnpm rag:answers`, если такой отчёт уже создан.

Полный воспроизводимый прогон (приложение и локальный сервис должны работать):

```bash
pnpm rag:answers
```

Скрипт вызывает тот же `/api/chat`, который использует агент, фиксирует версию
индекса на весь прогон, чередует порядок режимов и сохраняет 20 ответов, время,
токены, найденные источники и ссылки. При неполном ответе или сбое полный отчёт
не публикуется, промежуточные результаты остаются в
`.local-data/rag/answer-runs/<run_id>/progress.json`. URL приложения можно задать
через `RAG_CHAT_URL` (по умолчанию `http://localhost:3000/api/chat`).

После успешного прогона создаются полный отчёт `rag/answers-comparison.md`
и машиночитаемые ответы `rag/answers-comparison.json`. Качество оценивается вручную:
по одному баллу за каждый ожидаемый факт и отдельная отметка неподтверждённых
утверждений. Оценки в `rag/answer-review.json` привязаны к run_id и SHA-256
ответов, поэтому новый прогон не наследует оценки старого. После ручного
заполнения оценки пересоберите отчёт без повторных запросов к LLM:

```bash
pnpm rag:answers --render
```

Небольшой контрольный набор и один прогон демонстрируют поведение на нашей базе;
результат не является универсальной оценкой модели. Высокий score поиска или
существующий ID цитаты не гарантируют, что ответ подтверждён источником.

## Реранкинг, фильтрация и query rewrite (день 23)

Режим **RAG + обработка** использует два этапа поиска. Сначала локальная
Qwen2.5:1.5b выделяет дословные ключевые фразы. Исходный вопрос сохраняется целиком,
без перевода и замены неоднозначных слов; фразы лишь дописываются в конец.
Фразы, которых нет в вопросе, отклоняются с возвратом к исходному запросу.
Исходный и расширенный запросы
ищутся независимо; результаты объединяются по chunk_id через Reciprocal Rank
Fusion (RRF). Затем cross-encoder заново оценивает пары «исходный вопрос — чанк»,
переставляет кандидатов и применяет порог. Затем локальная Qwen2.5:7b проверяет,
есть ли в каждом прошедшем чанке факты для ответа. Она выбирает номера отрывков;
код берёт точные цитаты из исходного текста и проверяет их наличие.
После проверки удаляются повторные цитаты и одинаковые фрагменты. Дополняющие
факты, разные числа и отрицания сохраняются. Только после этого применяется
итоговый top-K: это максимум, отвергнутые фрагменты не добираются.
Окончательная LLM получает исходный вопрос и отобранные источники.

Реранкер — [mmarco-mMiniLMv2-L12-H384-v1](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1),
многоязычная модель с поддержкой русского, зафиксированная по revision в
`scripts/rag/models.mjs`. ONNX-инференс работает на CPU через Transformers.js;
на пару отводится 512 токенов, длинные пары обрезаются. Скачиваются только
официальные артефакты; при поиске сеть для реранкера отключена.

Подготовка (Ollama должна работать в отдельном терминале):

```bash
pnpm install
pnpm rag:ollama
# В другом терминале:
pnpm rag:models
pnpm rag:index
pnpm rag:server
```

`rag:models` скачивает около 120 МБ весов реранкера, токенизатор и около 1 ГБ
локальной модели rewrite, а также около 4,7 ГБ модели проверки цитат Qwen2.5:7b.
Они и кеши находятся в `.local-data/rag/`, вне Git.
Rewrite и rerank не отправляют содержимое проекта наружу. Финальная генерация,
как и прежде, отправляет вопрос и выбранные чанки в DeepSeek.

Настройки сохраняются с агентом:

- `topKBefore`: размер каждого векторного поиска и объединённого списка (1–50, по умолчанию 24).
- `topKAfter`: максимум источников после обработки (1–10, по умолчанию 5).
- `rewrite`, `rerank`, `filter`: независимые переключатели.
- `minRerankScore`: порог sigmoid(logit) реранкера (0…1). Это не вероятность правильности.
- `verifyEvidence`: проверка подтверждающих цитат (по умолчанию включена).
- `deduplicate`: удаление повторяющихся источников/цитат (по умолчанию включено).
- `minSimilarity`: порог cosine similarity (−1…1), применяется только при отключённом реранкере.

При недоступности rewrite остаётся поиск по исходному вопросу, причина видна
под ответом. Ошибка реранкера или проверки цитат останавливает запрос с подсказкой о подготовке
модели. Если все результаты ниже порога или без подтверждающих цитат, LLM получает пустой контекст и должна
сообщить, что подтверждений нет. Тематически близкий источник не обязательно
содержит запрошенный факт: даже высокий rerank score не заменяет проверки ответа.
Метаданные показывают оба поисковых запроса, модели, similarity, отдельный
rerank score и ранг кандидата до реранкинга. Бюджет источников — 18 000 символов.
Старые сохранённые настройки без поля rerank продолжают использовать прежнюю
эвристику rewrite и similarity-фильтр; включение нового режима задаёт новую конфигурацию.

Страница **Сравнение RAG** (`/rag-comparison`) объединяет обычное сравнение и
фильтрацию: три колонки ответов **Без RAG — С RAG — С RAG + обработка**,
вопрос расположен над ними. Старый адрес `/rag-filter-comparison` перенаправляет
на общую страницу. Есть выбор набора:
исходные 10 вопросов, новые 10 для настройки (dev), новые 10 для проверки (test).
В `rag/extended-questions.json` записаны ожидания, источники и ссылки на эталоны.
Наборы разделены по темам и включают перефразированные вопросы, вопросы к коду,
составные вопросы и близкие к теме вопросы, ответа на которые в базе нет.

Все три режима используют одинаковые модель и температуру, без истории, памяти,
профиля и MCP. Два режима RAG используют один снимок индекса.
Средняя колонка повторяет пайплайн дня 22: исходный вопрос → embedding →
косинусный поиск top-5 (overlap) → контекст до 18 000 символов → LLM.
Запрос не содержит `ragSearch` и вызывает `action: search`, без нового пайплайна
обработки; инструкции модели совпадают с днём 22. Все настройки, включая top-K,
относятся только к правой колонке. Сохранённые ответы показывают настройки своего прогона.
При загрузке старого прогона новые переключатели включены для следующего запуска.
Запуск выполняет 30 запросов DeepSeek. Результаты сохраняются в браузере;
смена набора или новый запуск заменяет показанный прогон. При первом открытии
переносится последний сохранённый прогон из прежних страниц: колонки сохраняют
свой смысл, отсутствующий режим остаётся незапущенным. Старые ответы средней
колонки с метаданными обработки требуют нового прогона и не показываются как
RAG дня 22. Новые результаты сохраняются в ключе v3; старые ключи v1/v2
не удаляются.

Под источниками видны этапы: найдено → прошло порог → с цитатами → без повторов
→ передано модели. Точность текста цитаты гарантируется проверкой, но её смысловую
релевантность оценивает модель: возможны ложные допуски и отказы.
Проверка всех кандидатов до top-K добавляет задержку. Результаты кешируются по
вопросу, тексту, digest модели и версии промпта; документы остаются локально.

Повторная локальная проверка новых этапов на 20 известных вопросах:

```bash
pnpm rag:evidence
```

Она сохраняет `rag/evidence-comparison.json` и `.md`, сравнивая на одном снимке
поиск с новым rewrite до и после проверки цитат и дедупликации. В отчёте —
количество источников, попадание размеченных фрагментов и отказы для вопросов без
ответа. Это регрессия на известных вопросах, не новый слепой holdout и не оценка
ответов DeepSeek. Прежние отчёты не перезаписываются.

Для воспроизводимой локальной оценки первых этапов (без проверки цитат и дедупликации):

```bash
pnpm rag:calibrate  # только dev, сохраняет параметры и хеши моделей/данных
pnpm rag:benchmark  # test с зафиксированными параметрами + исходные 20 вопросов
```

Калибровка выбирает порог по Hit@5, затем по отсечению вопросов без ответа и
MRR, затем уменьшает число чанков; при равенстве выбирает меньший порог. Отложенные вопросы в подборе не
участвуют. Проверка требует тот же снимок индекса, набор вопросов и версии
моделей. Результаты: `rag/rerank-calibration.json`, `rag/rerank-comparison.json`
и `rag/rerank-comparison.md`. Сравниваются baseline, rewrite, rerank, их сочетание
и сочетание с порогом. Исходные 20 вопросов дня 21 сохранены для регрессии.

Это метрики поиска (Hit@5, MRR, precision по разметке, отсечение и число чанков),
а не готовых ответов. Разметка не исчерпывает всех правильных источников; JSON
показывает покрытие эталонов и фрагменты, пересекающие границы чанков.
При шести положительных вопросах в test вывод предварительный. Качество ответов
проверяется отдельно по ожидаемым фактам, цитатам, выдуманным утверждениям и
корректным отказам. Старый `pnpm rag:relevance` оставлен для воспроизведения
эвристического подхода с фиксированными прежними параметрами (12 → 5, 0,45).

Генерация и сохранение ответов на проверочные 10 вопросов:

```bash
pnpm rag:enhanced-answers
```

Команда выполняет 20 запросов DeepSeek и сохраняет `rag/rerank-answers-comparison.json`
и `.md`. На странице сравнения кнопка «Отчёт с обработкой» загружает этот
прогон в две правые колонки; «Отчёт без/с RAG» загружает отчёт дня 22 в две левые. Ручные оценки фактов привязываются к run_id и хешам ответов в
`rag/rerank-answer-review.json`; `pnpm rag:enhanced-answers --render` пересобирает
отчёт без новых запросов. Ожидания видны в раскрывающемся блоке вопроса.

## День 24 — ответы с цитатами в чате

В обычном чате выберите **Режим ответа → RAG с цитатами · день 24**.
Режим использует настроенный поиск дня 23 и возвращает ответ, список использованных
источников (`source`, `section`, `chunk_id`, строки) и дословные цитаты для каждого
утверждения. Источники и цитаты находятся прямо в ответе и сохраняются в истории.
Ниже отдельно доступны найденные фрагменты: их наличие ещё не означает, что они
подтвердили ответ. Новые ответы третьей колонки страницы сравнения также используют
день 24. Средняя колонка и режим **С RAG · день 22** сохраняют прежнее поведение.
Старые сохранённые ответы не становятся проверенными автоматически.

Пайплайн:

1. Поиск/обработка возвращают чанки. При отсутствии чанков выше порога ответ
   «Не знаю» формируется сервером без генерации и содержит просьбу уточнить
   компонент, версию или сценарий либо добавить документ. Даже при отключённом
   фильтре режим дня 24 применяет порог перед ответом и проверяет его для каждой
   используемой цитаты. При реранкинге используется `minRerankScore`, иначе
   `minSimilarity` (по умолчанию 0.45).
2. Модель получает каталог отрывков и возвращает JSON с отдельными утверждениями
   и ссылками `source_id + quote_id`. Текст цитат подставляет сервер из чанков:
   модель не перепечатывает код и не может изменить пробелы, числа или отрицания.
3. Сервер проверяет структуру, существование источников и отрывков, точное
   вхождение цитаты в чанк и порог релевантности. Метаданные источников берутся
   из индекса, а не из ответа модели.
4. Локальная Qwen2.5:7b проверяет **каждый факт только по его собственным
   цитатам**, без исходного вопроса и соседних утверждений. Проверка отдельно
   называет объект цитаты и объект утверждения, сопоставляет условия и область
   действия; при несовпадении `supported` заменяется на `insufficient`. Три результата:
   `supported` — подтверждён, `contradicted` — противоречит цитате,
   `insufficient` — доказательств недостаточно. Отсутствие определения константы
   не считается противоречием. Число, отсутствующее во всех цитатах факта,
   консервативно получает `insufficient`: нужна цитата с определением значения.
   Для числового ограничения из кода одних деклараций констант недостаточно:
   нужна также цитата применения к нужному объекту. Эти консервативные правила
   могут отклонять корректные сведения, вычисления и пересчёты единиц. Черновик до
   проверки пользователю не передаётся.
5. Отдельный запрос к Qwen оценивает полноту ответа. Сервер выделяет до шести
   частей вопроса по пунктуации и связкам; модель обязана сопоставить каждую
   с проверенными фактами (`full` / `partial` / `unanswered`). Она не пересматривает
   истинность фактов. Неотвеченные и частично отвеченные части попадают в уточнение
   дословно из вопроса; произвольные сведения модели туда не добавляются.
   Разбиение эвристическое, оценка покрытия остаётся вероятностной.
6. Допускается одно исправление. При недостатке доказательств или неполном ответе
   выполняется не более одного дополнительного поиска по тому же `build_id`:
   8 кандидатов → до 3 чанков, до 8000 символов сериализованных источников.
   Сохраняются пороги исходного поиска; используются недостающие части вопроса,
   неподтверждённые утверждения и имена констант из их цитат. Найденные чанки
   не считаются доказательством автоматически: новые утверждения снова проходят
   проверку дословности и смысла. Дополнительные источники видны под ответом и
   сохраняются в истории; их номера продолжают исходные `[S1]…`.
7. Проверенные релевантные факты сохраняются при неудачном исправлении.
   `supported` — ответ признан полным; `partial` — подтверждённая часть с цитатами
   и уточнением пробелов; `unknown` — нет подтверждённых релевантных фактов,
   «Не знаю» с пустыми списками источников и цитат. Сбой смысловой проверки до
   получения подтверждений возвращается как ошибка, а не отсутствие знаний.
   Если релевантные подтверждения уже получены, сбой дополнения или оценки полноты
   сохраняет их с явным сообщением о незавершённой проверке. Новые факты, чья
   уместность ещё не проверена, при сбое оценки полноты не публикуются.

API: `useRag: true, ragGrounding: true`, опционально `ragSearch` и `ragBuildId`.
Внутренний формат генерации — JSON, окончательный формат выбирается как прежде:
текст, JSON, XML или YAML. MCP-инструменты в этом режиме не вызываются: фактическое
содержание должно подтверждаться базой документов. Ограничения задачи продолжают
проверяться существующим механизмом инвариантов. Максимум — 6 утверждений и две
цитаты на каждое; неудачное исправление не запускает бесконечные повторы.

Для локальной проверки 10 вопросов:

```bash
pnpm rag:ollama
pnpm rag:models
pnpm rag:grounding
```

Команда использует известные 10 test-вопросов, текущий снимок индекса и **только
локальные модели**: Qwen2.5:7b для генерации и выбранный профиль для проверки
фактов и полноты (по умолчанию тоже 7B). Эталоны модели не передаются.
Результат: `rag/grounding-comparison.json` и `.md`; для каждого вопроса записаны
наличие источников/цитат, три вида смысловых вердиктов, отдельная оценка полноты, попытки исправления,
финальный ответ или отказ. Незавершённый прогон остаётся в `.local-data/rag/grounding-progress.json`.
Это проверка механизма, не оценка качества DeepSeek: генератор и проверяющий
могут использовать одну локальную модель и разделять ошибки. Проверка дословности
детерминирована; смысловая проверка вероятностная и допускает ложные отказы и
ложные подтверждения. Наличие цитат не гарантирует полноту ответа.

Состояние до разделения проверок сохранено в `rag/grounding-before-partial.json` и `.md`. Сравниваются те же вопросы и тот же индекс; оценки Qwen требуют ручной сверки с цитатами.

### Локальный проверяющий Qwen3.5 27B

Финальная проверка фактов и полноты может использовать `qwen3.5:27b-q4_K_M`.
Отбор чанков по цитатам по-прежнему использует Qwen2.5 7B, rewrite — 1.5B,
эмбеддинги — прежнюю embedding-модель. Индекс перестраивать не требуется.
Профиль финального проверяющего хранится в `.local-data/rag/grounding-config.json`;
при отсутствии файла используется 7B. Сервер читает настройки при запуске.

```bash
pnpm rag:models --grounding-27b
pnpm rag:judge:configure --model=qwen3.5:27b-q4_K_M --think=false
# Перезапустите локальный RAG-сервис:
pnpm rag:server
```

27B получает контекст 8192 токена. Обычный режим имеет лимит вывода 1500 токенов,
thinking — 4096 с отдельным полем reasoning; парсится только финальный JSON из
`message.content`. Обрезанный или некорректный результат не считается подтверждением.
Параметры sampling соответствуют выбранному профилю и записываются в отчёт.
Возврат на прежний проверяющий: `pnpm rag:judge:configure --model=qwen2.5:7b --think=false`
и перезапуск RAG-сервиса. Автоматического перехода в облако нет.

Для сравнения именно проверяющих, без повторной генерации ответов:

```bash
pnpm rag:judge:compare --profile=7b
pnpm rag:judge:compare --profile=27b
pnpm rag:judge:compare --profile=27b-thinking
```

Фиксированный набор `rag/grounding-judge-cases.json` содержит 19 утверждений
(7 сохранённых примеров и 12 новых синтетических) и 5 проверок полноты.
Разметка выполнена Codex до сравнения, не передаётся моделям и не является
независимой человеческой оценкой. Для оценки самой модели числовые guardrails
отключены одинаково во всех профилях; рабочий сервис всегда включает их.
Отчёты `rag/grounding-model-*.json` содержат вердикты, ошибки, время, параметры,
хеши набора/модели/промптов и снимки памяти Ollama. Thinking проверяется отдельно
на трёх заранее выбранных сложных утверждениях и одном случае полноты; сравнивать
его нужно с теми же строками других профилей. Незавершённые прогоны сохраняются
в `.local-data/rag/judge-*-progress.json`.

Результаты локального сравнения: [7B и 27B](rag/grounding-model-comparison.md).
На зафиксированном наборе обычная 27B дала 0 ложных подтверждений вместо 2,
но 2 лишних отказа вместо 0; полнота — 5/5 вместо 2/5. Медиана проверки одного
факта выросла с 2,8 до 15,8 с. Это сравнение проверяющих, не всей цепочки RAG.
Thinking-пилот остановлен после первого таймаута 240 с; его качество не оценено.
При ошибке thinking-пилот завершается досрочно с `complete=false` в отчёте.
