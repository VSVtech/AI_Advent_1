# ADR 0001. Лексический BM25-поиск вместо эмбеддингов для AI-ревью PR в CI

## Статус

Принято. Автоматическое AI-ревью PR — день 32; реализация в
`scripts/review/lexical-search.mjs` и `scripts/review/review-pr.mjs`.

## Контекст

На каждый pull request GitHub Action `.github/workflows/ai-review.yml`
(`on: pull_request_target`) запускает `scripts/review/review-pr.mjs` и публикует
ревью в комментарий PR. Ассистенту нужен контекст по проекту: сам diff и список
изменённых файлов из ревью исключаются, а пояснения берутся из корпуса
`rag/corpus.json` (README, `docs/`, исходники).

Обычный RAG проекта (дни 22–30) построен на эмбеддингах: `qwen3-embedding:0.6b`
в локальном Ollama, 1024-мерные векторы, точный cosine similarity по
нормализованным векторам, индекс в `.local-data/rag/builds/<build_id>/`
(README.md:505, README.md:539). Такой пайплайн требует Ollama, скачивания модели
и предварительной индексации, то есть состояния на runner'е.

Ограничения, заданные окружением CI:

- workflow работает с секретом `DEEPSEEK_API_KEY` и использует
  `pull_request_target`; workflow и скрипт ревью берутся из базовой ветки,
  коммиты PR только скачиваются как git-объекты и читаются как diff, без
  checkout, установки зависимостей и запуска (README.md:1070-1074,
  ai-review.yml:3-6, 30-42);
- каталог репозитория в CI — только исходники, кеша индекса и локального Ollama
  там нет;
- контекст в промпте ограничен `MAX_CONTEXT_CHARS = 14 000` и разбит по
  бюджетам `MAX_DIFF_CHARS = 60 000` / `MAX_FILE_DIFF_CHARS = 12 000`
  (review-pr.mjs:16-18), поэтому нужен дешёвый по времени ранжировщик;
- шаг генерации ревью помечен `continue-on-error: true` — сбой поиска не должен
  требовать внешних сервисов (ai-review.yml:44-51).

## Решение

В CI используется собственный лексический BM25-поиск по тому же корпусу, что и
обычный RAG, без Ollama и без эмбеддингов (`lexical-search.mjs:1`):

- **Токенизация.** Идентификаторы режутся по camelCase и snake_case, текст
  приводится к нижнему регистру (`toLocaleLowerCase('ru-RU')`), берутся слова
  длиной от 3 символов, стоп-слова (код и русский/английский служебный набор)
  отбрасываются (lexical-search.mjs:5-19). Это позволяет находить по diff
  `getWeatherSummary` фрагменты про «weather summary».
- **Чанкинг.** Файл режется по 40 строк с предпочтением разреза по пустой строке
  во второй половине окна; чанк хранит `source` и номера строк
  (lexical-search.mjs:21-43).
- **Индекс.** Строится в памяти: частоты терминов по чанкам, документные частоты
  и средняя длина документа (lexical-search.mjs:45-63).
- **Ранжирование.** BM25 с `k1 = 1.4`, `b = 0.75`, IDF
  `log(1 + (N - df + 0.5) / (df + 0.5))`; повтор термина в запросе учитывается
  логарифмически (lexical-search.mjs:70-97).
- **Запрос и отбор.** `retrieveContext` строит запрос из путей изменённых файлов и
  добавленных строк diff (первые 8000 символов), изменённые файлы исключаются из
  контекста через `exclude` (review-pr.mjs:95-104). Из 60 лучших попаданий
  резервируются места отдельно для документации (`.md`) и кода, чтобы
  похожий код не вытеснил README/docs, затем результат укладывается в
  `MAX_CONTEXT_CHARS` (review-pr.mjs:105-116).
- **Источник корпуса.** `loadCorpusChunks` читает `rag/corpus.json` и молча
  пропускает отсутствующие файлы (`ENOENT`), поэтому неполный checkout не ломает
  ревью (lexical-search.mjs:99-113).

## Последствия

Плюсы:

- В CI нет Ollama, скачивания embedding-модели и шага индексации: поиск —
  чистый JS поверх файлов репозитория, работает на стандартном `node` 22
  (ai-review.yml:35-37).
- Индекс строится на каждый запуск в памяти из явного списка файлов, поэтому нет
  расхождения между индексом и содержимым базовой ветки и не нужно кешировать
  состояние на runner'е.
- Модуль покрыт юнит-тестами: токенизация, чанкинг с номерами строк, ранжирование
  и `exclude` (tests/ai-review.test.ts:57-80).
- Исключение изменённых файлов и раздельные квоты для docs/кода дают
  предсказуемый состав контекста (review-pr.mjs:103-111).

Ограничения и цена:

- Лексический поиск не находит синонимы и перефразирования: совпадение идёт
  только по общим термам после нормализации, тогда как RAG проекта использует
  эмбеддинги и cosine similarity (README.md:539).
- Качество зависит от токенизации: слова короче 3 символов и стоп-слова
  игнорируются, поэтому очень короткие имена в diff не дадут попаданий
  (lexical-search.mjs:17-18).
- Полнотекстовый индекс строится заново на каждый запуск: на текущем размере
  корпуса (rag/corpus.json:4-63) это дёшево, но растёт линейно с корпусом.
- Две разные реализации поиска (embedding-RAG для чата и BM25 для ревью)
  нужно поддерживать параллельно; общий у них только формат корпуса
  `rag/corpus.json`, а чанкинг в lexical-search.mjs:21-43 отличается от
  стратегий чанкинга обычного RAG (README.md:520-526).
- Корпус в `rag/corpus.json` — явный список файлов, поэтому новый документ без
  записи в манифест в контекст ревью не попадёт (например, этого ADR там нет).

## Альтернативы

1. **Использовать embedding-RAG и в CI (Ollama + `qwen3-embedding:0.6b`).**
   Дало бы семантический поиск, но требует установки и запуска Ollama и
   предварительной индексации на runner'е, что противоречит принятой в workflow
   модели «PR-код не устанавливается и не запускается»
   (ai-review.yml:3-6, README.md:1070-1074).
2. **Скачивать готовый индекс или векторы из артефактов/кеша.** Убирает время
   индексации, но добавляет состояние и риск расхождения индекса с базовой
   веткой; сейчас индекс детерминированно строится из `rag/corpus.json`
   (lexical-search.mjs:99-113).
3. **Передавать в модель весь корпус или весь diff без отбора.** Не проходит по
   бюджету `MAX_CONTEXT_CHARS = 14 000` и лимитам diff
   (review-pr.mjs:16-18), а также раздувает стоимость вызова DeepSeek.
4. **Гибридный поиск (BM25 + эмбеддинги).** Возможное развитие, но требует
   эмбеддингов в CI, то есть упирается в то же ограничение, что и вариант 1.
